# 审计子代理协议模板（skill-audit 用）

> 派子代理时逐字带上本协议（或按审计对象裁剪视角清单）。两次实战验证：六支线审计 + 全盘四视角审计，累计挖出 70+ 真实问题。

## 通用协议（每个子代理都要带）

```
你是技能架构审计员。深度审计 [审计对象] 的 [视角名]，找出系统性缺陷并给升级建议。

[对象路径清单：列出该视角要读的文件；要求「SKILL.md 全文读，脚本读 docstring/关键函数/相互调用，不逐行读实现」]

审计维度（每条问题给文件名+原文位置/行号，没问题的维度明确说「无」）：
[按视角填 4-6 个维度，见下方视角库]

纪律：
- 只报你真实读到的内容；没读到的不猜
- 每条问题必须有证据（文件名+行号/原文）
- 与别的视角结论冲突时保留矛盾，标注「待交叉印证」
- 输出结构化清单 + Top 5 升级建议（按价值排序，注明改哪里）
- 任务预算（防超时，派发方已按此裁剪）：本视角限读 2-3 个文件（清单里选最相关的）；候选缺陷 ≤15 条，超出按价值截断
- 主文件 >300 行时派发方已给行段清单：只读指定行段，不读全文；读不到的维度标「未读，主线程补」
```

## 视角库（按审计对象选 3-4 个）

### A. 主线流程（多步骤管线/状态机类技能）
1. 步骤衔接：状态机/阶段流转与各步骤文档描述是否一致？「文档说的步骤脚本不支持」或反向？
2. 流程断点：缺文件/重入/中断恢复/序号错位时会不会卡死？防呆够不够？
3. 职责重复：步骤之间、步骤与支线之间重叠？
4. 表述漂移：各步骤文档之间、与主文档之间流程描述不一致（旧命令/旧流程/触发词）？
5. 效率：每步里 AI 手做的事哪些还能脚本化？

### B. 脚本与数据（脚本较多的技能）
1. 数据流一致性：字段在生产者/消费者之间名一致？死字段（写不读）？
2. 错误处理：失败模式都有明确报错？静默吞错会让 AI 误判成功？
3. 幂等性：重复执行会破坏状态吗？缺防重？
4. 职责重复/孤儿：同一逻辑多处实现？无调用方脚本？
5. 依赖脆弱：cwd 隐式依赖、文件名约定、环境依赖？

### C. 编排路由（有子技能/触发词体系）
1. 路由完整性：主触发词表与子技能 frontmatter 双向覆盖？断头路由？
2. 触发词歧义：多子技能触发词重叠？边界/NOT-for 写清？
3. 结构一致性：references 有孤儿（无人引用）？引用路径分裂？
4. 编排逻辑：主流程的通用规则在支线/子代理场景是否成立？旧铁律残留？
5. 文档膨胀：主文档与子文档重复段落，可精简为引用？

### D. 质量闭环（带检测/评审机制的技能）
1. 检测重复：同一维度多处检测？互补（粗筛+精审）还是冗余维护？
2. 闭环缺口：检测发现问题后修复入口存在？「打回」路径真的会走到修复？
3. 分级一致性：warning 级别语义一致？该硬拦的没拦、该软的硬拦？
4. 数据闭环：质量数据（趋势/评分/审稿结果）是否反哺下一轮？
5. 咬合错位：前置约束（写前避雷）与事后检测清单是否同一套？只避不检/只检不避？

### F. 确定性 lint（先跑脚本，不派子代理）
跑 `{SKILL_DIR}/scripts/audit_lint.py <技能目录>`，判据见 `references/lint-checks.md`（L1-L8）。
脚本命中直接进候选清单；L3/L4/L5 的命中作为子代理「待判断」输入。

### G. 契约同步（有权威路径脚本/脚本间字段往来的技能加）
1. **权威路径同步**：SKILL.md 声明的「权威路径脚本」（流程仪表盘/批量执行器）内部打印/硬编码的步骤清单，与 SKILL.md 各步骤是否一致？SKILL.md 加的步骤在权威路径输出里丢没丢？（novel-writer 案例：chapter_flow.py 硬编码清单漏了 SKILL.md 新增的写前纪律）
2. **跨脚本数据契约**：字段在生产者（生成文件的脚本）与消费者（解析文件的脚本）之间的**标签名**是否一致？写「身份」读「identity」这类错位（novel-writer 案例：tracking_commit 生成字段 vs assemble_spec 期望字段——当场验证过一致才通过）
3. **声称 vs 实现**：脚本 help/文档声称的参数与功能，逐项在实现里存在吗？SKILL.md 说「查 X」但脚本没有 X 参数？
4. **通用/特定分层**：领域规则硬编码在代码里还是数据里？通用机制（状态机/引擎）与领域内容（词表/阈值/模板）有没有混在一起？（硬编码规则 → 建议抽数据，改规则不该改代码）
5. **路径硬编码**：文档/脚本里有没有写死机器绝对路径？（通用层应只靠占位符 + `Path(__file__)` 自定位）

## 汇总排序规则（主线程做，子代理不碰）

- 交叉印证升级：≥2 个视角同时命中 → 最高优先
- 严重度：🔴 流程闭环断裂（检测不阻断/静默吞错）> 🟠 数据正确性 > 🟡 幂等/重复 > 🔵 文档漂移
- 修复顺序：P0 数据正确性 → P1 幂等收敛 → P2 编排文档

## v2 增补（2026-08 GitHub 调研吸收）

### 反证协议（假阳性拦截门）

派反证子代理时用：
```
你是反证审计员。下面是一份候选缺陷清单。你的任务不是找新问题，而是逐条尝试推翻它：
- 读候选所指的文件与行号，验证证据是否真实存在（行号对得上、原句对得上）；
- 判断「这算不算缺陷」：对照该技能的成立条件与预期行为，候选是否把「设计取舍」误报为「缺陷」？
- 推不翻的保留（写「成立」），推得翻的写「误报：理由」。
输出：每条候选给「成立/误报」+ 一句话理由。不得为了推翻而推翻，也不得为了保留而放水。
```

### 强制证据门槛（写进每个视角协议）

每个候选缺陷必须四要素齐全，缺一不算缺陷：
1. 文件路径 + 行号（或函数名）
2. 原句/原代码（逐字摘录）
3. 缺陷类型（对照视角维度）
4. 触发方式：怎么验证它存在（跑什么命令/读哪个字段会出现什么）

### 安全对抗视角清单（第 5 视角，涉外部输入/下载/凭据的技能加）

- 提示注入：SKILL.md 或脚本是否把外部输入拼进命令/prompt？
- 数据外泄：是否把敏感数据发往未授权端点？
- 供应链：脚本是否从不可信地址下载执行（curl | bash）？
- 凭据处理：密钥硬编码/误日志？
- 权限放大：脚本是否申请超出职责的权限？

### 规范符合性检查单（结构视角内嵌，低成本高命中）

- frontmatter：name kebab-case 且与目录一致、description ≤1024 字且含「做什么/触发词/不触发」三要素
- 触发词：双向覆盖（主表有子有、子有主有）
- 渐进披露：SKILL.md <300 行，细节下沉 references/scripts
- 反模式：无「建议/可以考虑」软化词、无写死 runtime
### E. 使用者三视角（任何审计都可加，零成本清单）

派一个子代理轮流用三个角色读 SKILL.md/主文档，各挑 1-3 个问题：
1. **使用者（agent）视角**：第一次触发这个技能的 agent 会怎么误解哪一步？触发词会误命中什么场景？哪条指令会被忽略或执行错？
2. **维护者视角**：三个月后回来改这个技能的 agent 会踩什么坑？（隐式约定没写、状态文件格式没文档、改动会破坏哪里不知道）
3. **新手视角**：完全不了解背景的用户第一次看这个技能，哪里读不懂、哪里缺上下文？
